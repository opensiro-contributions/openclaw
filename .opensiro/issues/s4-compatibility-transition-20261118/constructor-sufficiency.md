## Smallest combined native construction, not a generic controller

1. **Future event input:** one official vendor/SDK release/deprecation notice URL, publication/effective dates and affected API/version ranges; treat content as untrusted, enforce source provenance and staleness/UNKNOWN, no model-generated maintainer authority. Do not guess an unknown future date.
2. **Original-native matching:** use `src/plugins/status.ts` compatibility/loaded report, installed plugin ID/version/source, `src/plugins/sdk-deprecation-notices.ts` records, and the native update-availability work in original [#131897](https://github.com/openclaw/openclaw/issues/131897) / [RFC #66](https://github.com/openclaw/rfcs/pull/66) *if actually shipped*. Require exact candidate provenance and affected version; no false promise that an update exists.
3. **New opt-in read-only `plugin_transition_review`:** narrow typed current-plugin/future-event matching in the existing host-owned `system-agent` plugin inspection route, returning affected/unknown, allowed supported targets and `hold`, `propose`, `escalate` choices plus correlation ID. This is a **proposed** action, not a shipped API; avoid a separate scheduler, general purpose VSM controller or invented plugin-control privilege.
4. **C agent and authority:** a developer can compose a bounded host-scoped autonomous review actor to select among these options under parent-fixed constraints; a proposed installation goes only to existing direct-only system-agent exact host approval/typed installer. Operator is the **actual mutation authority**. No consent means no effect. The agent owns future option selection, not S3/S5 ultimate authority.
5. **Return/closure:** correlate the approved native operation result with `plugins doctor` and actual subsequent plugin load + plugin tool invocation. Return success/failure/unknown to the same reviewing actor for the next plan. Diagnostics or planned status alone do not close S4.

## Acceptance contract (proposed; NOT_RUN)

- **AC-01 positive prospective:** installed plugin `p@v1` using a real affected SDK surface; pinned authoritative announcement says retirement future date, supported `p@v2` available; review actor chooses propose; exact host approval granted; real subsequent plugin load + sample tool call succeed; later outcome is correlated to original decision. Observe user can decide and verify an upcoming transition rather than await local breakage.
- **AC-02 source invalid:** stale/fabricated release notes, missing version or source mismatch produce `UNKNOWN / HOLD`; no mutation and no definitive risk assertion.
- **AC-03 authority/denial:** agent cannot call ring-zero plugin write directly; rejected or mismatched host approval leaves installed plugin unchanged and records denial, not success.
- **AC-04 real closure:** proposed update fails install, loads but tool fails, or lacks after-operation telemetry: return failure/unknown to reviewer; no `C` success claim from Doctor output alone.
- **AC-05 compatibility:** a plugin with no future retirement and ordinary installed state remains unchanged; baseline `plugins doctor` and update flow stay usable.
- **AC-06 falsify extra work:** if ordinary first-party tool composition already satisfies identical future→choice→approved next operation→feedback test, record `NO_QUALIFIED_C_TARGET` for new edit, not a duplicate feature.
